01

Where everything sits

Your idea becomes signals and rules. OpenAlgo supplies the account and native data. Our layer translates and coordinates. The chosen engine simulates; Optuna searches.

The product we distribute

A maintained OpenAlgo source distribution containing the native UI, research services and engine connectors. Today it includes OpenAlgo integration changes; it is not an independently installable official OpenAlgo plugin.

What the user sees

Backtest & Optimize, inside their existing OpenAlgo account. Results return to that same screen. Engine libraries do not require a second trading website.

Current scope: 1–8 long NSE cash-equity signal CSV strategies, shared capital, per-strategy rules and allocations, daily/minute data, fixed backtests, Optuna search, saved results and a chronological later-period check.

02

Data comes through OpenAlgo

The interval is derived from the signals and execution rules. Available candles are reused; only missing required windows reach the connected broker.

The same native database

Historify is the authoritative market-data archive used by this workflow. Broker downloads are saved there and read back before calculation. An engine adapter does not download a separate price history.

Why saved prices also exist in a run

A run retains its exact input snapshot so later data refreshes cannot change an old result. This is reproducibility evidence, alongside the original CSV and engine version.

Release blocker: enforce verified calendar coverage before accepting a historical date range.

Daily versus minute rules, missing data and verified evidence
CaseCurrent behavior / evidence
Daily strategyDate-only signals with ordinary daily rules request daily candles. Targets/stops alone do not force minutes.
Intraday or mixed strategyTimestamps, clock rules or minute holding periods require 1-minute data. A mixed portfolio uses its finest required interval.
OptimizationPlan the union of required windows across all allowed holding settings; prepare data once and keep eligibility fixed across trials.
Cache / downloadReal Fyers daily downloads and exact Historify read-back are verified. The 61-candle minute acceptance run used existing prices; a fresh real broker-minute download is still an acceptance gap.
Missing historyA successful but sparse response can produce explicit fixed exclusions. Auth/network/server failures stop preparation with resumable progress.
Calendar OPEN GATEThe native seed covers 2025–2026, but research accepts older ranges. Add verified calendar-coverage admission; unknown weekdays must not silently become trading sessions.
Nautilus specificationsCurrent master-contract tick rules are supplied specifications, not verified historical tick rules. Keep incompatibilities explicit; never round broker OHLC to make it fit.

03

What gets installed, and how it evolves

Recommended first release: a public source package people run on their own computer or private server. Each installation retains its own account, broker connection and data.

One resource to share

One repository with tagged releases, a built source ZIP, checksum, installation guide and support matrix. The local ZIP already exists; public publication remains a separate action.

One maintenance responsibility

We maintain the UI, rules and adapters as OpenAlgo and engine versions change. Locks and contract checks make compatibility explicit. They do not automatically guarantee compatibility with every future version.

The update and rollback path
When something changesRequired maintenance path
OpenAlgo updateReview native API, schema, authentication and UI integration changes. Adapt only the integration points; run the recorded contract and full workflow checks.
VectorBT / Optuna / Nautilus updateUpdate the relevant pinned lock and adapter together. Compare fills, cash, costs and saved-result replay; document deliberate numerical differences.
Existing user upgradesStop app/worker → back up private data → install the tested revision → migrate if needed → verify old reports → restart. Keep a tested restore/rollback route.
Current evidenceCompatibility checks and a populated same-version reinstall passed. Cross-version migration, rollback and automatic updating are not yet verified.

Docker is implemented but its image/startup journey remains unverified. A hosted multi-customer service would additionally need customer isolation, exposed-service security and operational controls. It is outside this initial distribution plan.

What must be true before we go public

The architecture is implemented. The next milestone is a trustworthy self-hosted public preview: technical checks and a new-user journey both pass against one exact release candidate.

Automated checks include the Windows/Linux backend suites, focused UI tests, real native-engine calculations, process cleanup and exact evidence comparisons. These are local acceptance results; an unaided outside-user trial and a recorded public-revision CI run remain separate.

What can wait until after a narrow public preview
  • Docker as an advertised install option — verify build, first setup, durable volumes, restart and restore before promising it.
  • Automatic or cross-version updates — test migrations, old-report compatibility and rollback before advertising them. A first source preview can document manual installation.
  • More brokers and markets — expand the support table from actual account tests; add shorts, derivatives or margin only through explicit engine/data contracts.
  • Arbitrary strategy-code import, rolling walk-forward and additional dashboards — separate capabilities, not hidden promises in the CSV interface.
  • Hosted operation and live strategy deployment — separate products/permissions; neither is required to publish a local research distribution.

Recommendation: close the data and install gaps, then publish a clearly scoped public preview. Add capabilities as verified releases.
